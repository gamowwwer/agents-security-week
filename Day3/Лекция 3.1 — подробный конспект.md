# Лекция 3.1. AI Agent defense architecture

## 1. Главная идея

Безопасность агента — свойство архитектуры, а не фильтр перед моделью и не проверка перед релизом. Модель является только одним из компонентов. Защищать нужно весь execution loop: получение контекста, выбор следующего шага, вызов инструмента, выполнение действия и обработку результата.

Ключевой принцип лекции: **every boundary is a control point** — каждая граница между слоями является местом, где нужно проверять данные, права и допустимость действия.

## 2. Чем агент отличается от LLM

Обычная LLM получает текст и возвращает текст; побочных эффектов может не быть. Агент самостоятельно собирает контекст, хранит состояние, выбирает действия и вызывает инструменты с реальными правами.

Рабочее определение:

> Агент = LLM + контекст + состояние + инструменты + правила + цикл выполнения.

Поэтому вопрос безопасности меняется с «что модель сказала?» на «что система сделала?». Даже безобидная текстовая ошибка становится инцидентом, если она запускает shell-команду, меняет CI-конфигурацию или отправляет данные наружу.

## 3. Пять слоёв агента

### 1. Input / Context

Всё, что агент читает: запрос пользователя, документы, письма, PR, web-страницы, ответы API и сообщения других агентов.

Риски: prompt injection, скрытые инструкции, недостоверные данные, лишний контекст и утечки.

### 2. Agent Core

Модель, системные правила, планирование и выбор следующего шага.

Риски: goal manipulation, reasoning collapse, обход ограничений и неправильный выбор инструмента.

### 3. Memory / RAG

Краткосрочная память, долговременное хранилище, vector DB и retrieval.

Риски: memory poisoning, доступ к чужим данным, устаревший контекст и закрепление ложной инструкции.

### 4. Tools / MCP

API, плагины, skills, MCP-серверы и команды, которые агент может вызвать.

Риски: tool poisoning, подмена описания, чрезмерные permissions, небезопасные комбинации действий.

### 5. Execution / Infrastructure

Файловая система, shell, Git, CI/CD, cloud и сеть.

Риски: RCE, изменение инфраструктуры, кража секретов, persistence и exfiltration.

## 4. Атака находится «на стрелке»

Компонент может быть безопасен изолированно, но уязвимость возникает при передаче данных между слоями. Примеры границ:

- внешний документ → контекст модели;
- модель → выбор инструмента;
- инструмент → файловая система;
- результат MCP → память;
- агент → другой агент;
- CI → внешняя сеть.

Текст одновременно выступает данными и потенциальной командой. Документ, PR или письмо нужно считать данными, даже если внутри написано «выполни это немедленно». Право превратить текст в действие должно контролироваться системой.

## 5. Метод threat modeling

Предлагается следующий процесс:

1. Нарисовать поток данных через пять слоёв.
2. Отметить все границы между слоями.
3. На каждой границе спросить: «какой максимальный ущерб может причинить атакующий?»
4. Оценить blast radius — масштаб последствий.
5. Начать внедрение контролей с границ с наибольшим blast radius.

Такой подход помогает не утонуть в длинном списке атак. Приоритет определяется тем, что агент реально может сделать.

## 6. Capabilities и blast radius

Уровень риска растёт вместе с полномочиями:

1. Генерация текста.
2. Чтение контекста.
3. Предложение изменений.
4. Запись файлов.
5. Запуск команд.
6. Управление CI/CD и деплоем.

Минимальные контроли:

- read-only рабочая область — allowlist команд;
- запись в рабочую область — allowlist и human approval;
- произвольный shell — sandbox и approval;
- внешние API — короткоживущие узкие credentials и аудит;
- CI/CD и deploy — все перечисленные меры, review и уменьшенные права.

Human approval полезен только тогда, когда человек понимает конкретное действие, параметры и последствия. Формальное подтверждение длинного непрозрачного скрипта защиты не даёт.

## 7. «Летальная триада» как правило проектирования

Опасная комбинация:

- private data;
- untrusted input;
- outbound channel.

Пример атаки:

1. Агент читает недоверенный PR.
2. Скрытая инструкция воспринимается как задача.
3. Агент меняет CI-конфигурацию.
4. CI запускается с секретами.
5. Секреты уходят через внешний канал.

Каждый шаг может выглядеть как легитимная операция. Для предотвращения компрометации достаточно надёжно удержать одну границу: не давать секреты, запретить запись вне allowlist или закрыть egress.

## 8. Реальные прецеденты

### GitLab Duo

Скрытый prompt в merge request мог заставить ассистента сформировать внешний запрос и передать приватный код. Нарушена граница input → egress.

### GitHub MCP

Вредоносный публичный issue влиял на сверхпривилегированного агента, который имел доступ к приватным репозиториям и мог вынести данные в публичный PR. Нарушены границы agent core и tools.

### Cursor / CurXecute

Инъекция меняла конфигурацию MCP, после чего новый компонент автоматически запускался и приводил к удалённому выполнению кода. Нарушена граница tools → execution.

Общий вывод: реальные инциденты проходят по одной и той же цепочке input → core → tools → execution → egress. Продукты различаются, но архитектурные границы повторяются.

## 9. ADLC — Agent Development Lifecycle

Для обычного ПО SDLC управляет кодом, зависимостями и релизами. В агентной системе изменяются ещё инструкции, контекст, память, инструменты и привилегии. Поэтому нужен ADLC, который управляет поведением агента на всём жизненном цикле.

### 1. Design

Определить границы, допустимые действия и явно запрещённые зоны.

### 2. Tools

Использовать allowlist. Считать описание инструмента частью доверительной модели и проверять его происхождение.

### 3. Context

Хранить provenance. Любой внешний контент считать данными, а не инструкцией.

### 4. Memory

Проверять данные при записи и чтении, разделять пользователей и задачи, ограничивать срок хранения.

### 5. Identity

Не передавать агенту сырой секрет. Использовать отдельную идентичность и выдавать scoped credential непосредственно перед вызовом.

### 6. Gateway

Централизовать auth, policy enforcement, metadata validation и logging для tool calls.

### 7. Red Team

Регулярно атаковать собственную систему и превращать найденные сценарии в regression-тесты.

### 8. Observe

Собирать данные, необходимые для расследования: prompt, tool calls и аргументы, RAG-фрагменты, guardrail verdicts, request identity, токены/права, версию модели и routing decisions.

## 10. Привилегии как свойство системы

Анти-паттерн: передать агенту raw API key. При компрометации модели или контекста ключ можно раскрыть и использовать вне системы.

Рекомендуемый паттерн:

1. Агент выбирает логическую операцию, например `call(PROFILE_DB_RO)`.
2. Система проверяет actor, ресурс, цель и политику.
3. Credential broker выдаёт короткоживущий scoped-токен.
4. Токен добавляется вне контекста модели.
5. Вызов логируется и токен отзывается после операции.

Что разрешено, определяет policy layer, а не промпт.

## 11. Типовые анти-паттерны

- Защищать только LLM, игнорируя границы.
- Использовать один системный промпт для всех сценариев.
- Передавать агенту сырые ключи.
- Выдавать права через текстовую инструкцию.
- Считать внутреннего агента безопасным по умолчанию.
- Подтверждать выполнение кода, который пользователь не может проверить.
- Оставлять открытый MCP-endpoint в надежде, что его никто не найдёт.
- Один раз настроить guardrail и больше не тестировать.

## 12. Референсная архитектура

Поток выглядит так:

1. Пользователь обращается к Agent App.
2. Приложение управляет циклом действий и контекстом.
3. Вызовы LLM проходят через text checks и политики.
4. Инструменты доступны только через allowlist, auth и gateway.
5. Исполнение изолировано в sandbox.
6. ADLC охватывает design, tools, context, memory, identity, gateway, red team и observe.

Архитектура сочетает три приоритета:

- контроль на каждой границе;
- безопасность на всём жизненном цикле;
- первоочередная защита действий с максимальным blast radius.

## 13. Итог

Agent security — это развитие привычного DevSecOps для системы, где один из входов является произвольным текстом, а решения принимаются вероятностной моделью. Надёжность достигается не надеждой на «правильный ответ» LLM, а системными ограничениями: изоляцией, минимальными правами, контролем границ, безопасной идентичностью, наблюдаемостью и регулярным red teaming.
